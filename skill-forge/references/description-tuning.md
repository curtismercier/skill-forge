# Description tuning — the "pushy" pattern

**Last verified:** 2026-04-16. Anthropic's own skill-creator guidance may evolve — spot-check against https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md when in doubt.

## The core problem

Claude decides whether to use a skill by reading only its `name` and `description`. If the description is too generic or timid, Claude won't reach for the skill even when it should. Anthropic calls this "undertriggering" and explicitly recommends writing "pushy" descriptions.

## Anti-pattern: timid descriptions

```yaml
# Undertriggers. Claude won't reach for this unless the user literally says "dashboard".
description: A skill for building dashboards.
```

```yaml
# Also undertriggers. Too generic — could apply to anything.
description: Helper for API integrations. Use when the user needs help.
```

```yaml
# Dangerous: sounds specific but the trigger words are too narrow.
description: Use this skill when working with our internal Anthropic metrics dashboard.
```

## Pattern: specific + pushy + negative space

```yaml
description: Build a simple, fast dashboard to display internal data. Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a 'dashboard.' Covers both read-only summaries and interactive tables.
```

Three things this does right:

1. **Specific up front** — tells Claude what the skill *does* in the first sentence
2. **Pushy trigger language** — "Make sure to use this skill whenever..." explicitly instructs Claude to reach for it
3. **Covers adjacent phrasings** — "data visualization, internal metrics, display any kind of company data" captures how users actually ask the question (rarely with the exact skill keyword)

## The checklist for a good description

- [ ] First 10-15 words convey what the skill does (not what it helps with)
- [ ] Explicit trigger phrase: "whenever", "use when", "make sure", "always"
- [ ] Adjacent phrasings users might use instead of the literal skill name
- [ ] A "not for" clause if the skill has a narrow scope
- [ ] Length between 100 and 500 characters (`audit_skill.py` warns outside this range)
- [ ] No LLM-slop attributions ("generated by", "AI-powered", etc.)

## Before/after from the Modal LLM Inference skill

**v1 (undertriggered):**
```yaml
description: A skill for deploying LLMs on Modal with vLLM.
```

**v2 (triggers well):**
```yaml
description: Deploy production-grade LLM inference on Modal.com using vLLM, with current Gemma 4, MiniMax-M2.7, and other frontier models. Use this skill whenever the user mentions Modal deployment, vLLM serving, serverless GPU inference, OpenAI-compatible endpoints on Modal, or deploying any LLM to Modal.com — even if they don't explicitly say "skill" or "vLLM." Covers single-GPU simple deploys, multi-GPU tensor-parallel for 100B+ models, memory snapshots for cold-start reduction, and proxy authentication.
```

The v2 description is 584 characters — longer than typical, but every trigger word pulls weight. If a user says "I want to deploy a model to Modal" (without mentioning vLLM), Claude will still reach for this skill.

## Testing triggering (manual)

Anthropic's own skill-creator tool has an eval-query workflow. Short version: draft 5-10 queries a real user might type, feed them to Claude, and see whether the skill's description makes Claude consult the skill. If it doesn't, tighten the description.

You can sanity-check by asking Claude (yourself, in another session): "Given this description, when would you use this skill?" and see if the answer matches what you actually want.

## When to deliberately undertrigger

Rare, but: if a skill has actions that cost money (cloud deploys, paid API calls), you may want it to trigger only on explicit request rather than adjacent phrasings. In that case:

```yaml
description: Deploy production LLM infrastructure on Modal.com — spins up paid GPU resources. Use ONLY when the user explicitly asks to deploy to Modal. Do NOT trigger for general discussion of Modal or vLLM; for those, just answer from knowledge.
```

Explicit "do not trigger for X" language is effective.
