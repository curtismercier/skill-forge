# Anti-slop heuristics — how to catch LLM hallucinations in skill drafts

**Last verified:** 2026-04-16.

Every heuristic here came from a real failure mode encountered building skills. The `audit_skill.py` script checks many of these automatically; this doc explains the *why* so you can spot ones the linter misses.

## The root cause

When an LLM generates a draft skill for a domain it only half-knows, it fills in plausible-sounding values. The result looks correct at a glance and fails the moment anyone runs it. The failures cluster around these patterns:

## Pattern 1: suspiciously round numbers

Real pricing, real benchmarks, real metrics almost never end in `.00` or `.50`. If you see `$3.50/hr for H200 GPU time`, it's a hallucination — the real rate is something like `$4.54/hr` or `$0.001261/sec × 3600`. <!-- noqa: audit -->

**Rule of thumb:** if a number *feels* easy to remember, verify it. Hallucinations gravitate to round numbers because they're easier for the model to predict.

**Verify:** fetch the provider's current pricing page and diff. For Modal, `https://modal.com/pricing`. For HF Inference Endpoints, `https://huggingface.co/pricing`. `audit_skill.py` flags `$X.00/hr` and `$X.50/hr` patterns automatically.

## Pattern 2: plausible-but-wrong function names

LLMs predict what an API *might* look like based on patterns across codebases. This produces names that follow naming conventions but don't exist. Examples from real drafts:

- `modal.Image.debian_windows()` — real is `debian_slim`
- `Image.from_windows_registry(...)` — real is `from_registry`
- `modal.enter.snap()` — real is `@modal.enter(snap=True)` as a decorator argument

**Verify:** `python scripts/gh_research.py find <owner>/<repo> "<identifier>"`. If it returns 0 results, the name is likely fabricated.

**Diagnostic signal:** suspiciously "systematic" naming (four functions with parallel camelCase structure) in a domain where the real API isn't that clean.

## Pattern 3: generic AI attributions in footers

Look for these (these are illustrative — they're what the audit script catches): <!-- noqa: audit -->

- "Generated by [Agent Name]" <!-- noqa: audit -->
- "This document was produced by [Claude/Assistant/AI]" <!-- noqa: audit -->
- "As an AI language model..." <!-- noqa: audit -->
- Generic "Agent" attributions with no specific product identity

These are classic LLM-generated chaff. They add nothing and signal low-effort generation. Strip them.

## Pattern 4: fabricated HuggingFace repo IDs

LLMs hallucinate model names that follow the `<org>/<model>-<params><variant>` pattern but don't exist. Real risk because lazy verification (does `transformers.AutoModelForCausalLM.from_pretrained(ID)` work?) requires actually running Python against a network.

**Verify:** the model-lookup sub-skill in skill-forge (if the user is building a model-touching skill) or the HuggingFace Hub API directly:
```python
import requests
r = requests.get(f"https://huggingface.co/api/models/{repo_id}")
# 200 = exists, 404 = fabricated
```

**Diagnostic signal:** model names that don't appear in the `trending` or `most-downloaded` lists on the Hub but are cited with specific benchmarks. If the benchmark number looks too clean (see Pattern 1) AND the model ID is obscure, skepticism goes up.

## Pattern 5: stale version pins that look too clean

`vllm>=0.6.0` in a 2026 skill is almost certainly stale — it's an 18-month-old pin copied from an old example. The LLM picked the version number from training data without checking the current stable release.

**Verify:** `pip index versions <package>` or the package's GitHub releases. For PyPI packages, `python scripts/gh_research.py releases <owner>/<repo> 3` shows the most recent releases with dates.

**Rule of thumb:** if you're not sure why a specific version is pinned (what breaks without it?), update to the current stable.

## Pattern 6: "Last verified" dates that predate significant API churn

A skill dated "verified October 2024" discussing Modal 1.0 features (released ~February 2025) has an internal inconsistency. Either the date is wrong or the content is from training data. <!-- noqa: audit -->

**Diagnostic signal:** dates older than 6 months without explicit updates; `audit_skill.py` warns on 90+ day-old markers.

## Pattern 7: copy-pasted doc structure

If a generated doc has the exact paragraph structure of a well-known source but with different words, the LLM was pattern-matching rather than reasoning. Trust it less.

**How to tell:** does the doc's section order feel mechanical (introduction → overview → steps → conclusion) rather than task-driven? Does it repeat the same 3-sentence paragraph shape? Those are signals.

## Pattern 8: specific but unverifiable facts

"vLLM 0.19 improved throughput by 3× over 0.17 on H200" — very specific, completely unverifiable without source. The model produced it because "specific numbers sound more credible." Treat specific claims without citation as provisional.

**Fix:** either cite the source inline (`[benchmark link]`), caveat with "approximate" language, or remove.

## Pattern 9: decorator/import paths that resemble but don't match

`from modal import enter` vs the real `import modal; @modal.enter()`. Small syntactic variance, large correctness difference. Common because LLMs interpolate between Python import conventions.

**Verify:** open the package on GitHub and look for the exact import pattern used in tests or examples.

## Pattern 10: confident statements about deprecated features

LLMs don't always know what's been removed. A draft might confidently describe `modal.Stub` (renamed to `modal.App` in Modal 1.0) without flagging the rename.

**Verify:** search the canonical repo for the name. If it only appears in migration guides or changelogs, the feature is deprecated.

## The audit workflow

1. Run `audit_skill.py /path/to/draft/` — it catches the mechanical patterns (1, 3, 6, and some 2)
2. Read the draft critically, looking for Patterns 2, 4, 5, 7, 8, 9, 10
3. For every specific claim about an external API, run `gh_research.py find` to verify
4. For every specific number or benchmark, find the source or remove/caveat it
5. Only ship after all verified facts are sourced or dated

## The deeper point

The failure mode is not the LLM being "wrong." It's the LLM being *plausibly* wrong in ways that look correct at review time. Anti-slop work is about recognizing the shape of plausibility without substance. When a draft feels too polished, too symmetric, too easy to skim without spotting errors — that's the signal.

This applies to your own generated content too. A skill you drafted in 30 seconds that reads smoothly is more suspect than one you painfully hand-edited. Frictionless generation is the slop signal.
